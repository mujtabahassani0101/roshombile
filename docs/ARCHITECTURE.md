# Roshd architecture

The current sheet pipeline (1.1.31) uses the copied Young Scientist document scanner, capture gate and OMR engines. Android ships those original engine binaries unchanged. Roshd-specific routing, QR roster bindings, current PDF calibration, 75-question trimming and annotation are isolated in `native/roshd_adapter`; the engine trees are byte-identical to the source project. QR-proved orientation is passed through the source engine’s existing typed option for Roshd’s prints without header dots. See [the port and its measured limitations](YOUNG_SCIENTIST_ENGINE_PORT_1.1.31.md). Version 1.1.38 additionally compares source-reader results from registered channel/contrast representations in the app adapter. Recovered or conflicting choices require explicit review; the copied engines remain unchanged. See [ink verification](INK_VERIFICATION_1.1.38.md). Earlier scanner descriptions below record the previous implementations.

`ApplicationLoader` owns `ExamsController`, `ConnectionsManager`, encrypted `MessagesStorage`, `NativeGateway`, and `NotificationCenter`. Controller work uses a serial stage queue; view work returns to the Android main thread. `ActionBarLayout` and `BaseFragment` manage native navigation. These are independent Kotlin implementations influenced by the local Telegram architecture; Telegram services are not used.

`core/Roshd.kt` is the canonical HTTPS origin. Restored sessions must match that origin. The Android package, settings, encrypted SQLite database and Keystore aliases use Roshd-specific namespaces. This is an independent install and does not import another app's credentials or queues.

`ScannerActivity` captures full-quality answer-sheet photos with CameraX and four fixed A5 targets. The user aligns the printed squares with those targets. Live guidance samples luminance in the answer region and checks focus, content stability and a confirmed QR; it performs no document/fiducial search, model inference or optical-flow tracking. The retained `PaperframeScanner`, ARM MNN models, perspective correction and manual corner editor remain available for imported images and manual editing. Printed squares and paired rows register each saved photo independently in the native reader. Initial square search uses a small image, followed by original-resolution vertex refinement. Local thresholds tolerate lateral shadows and two narrow rail strips replace a full-page verification warp. Camera photos use a 2600-pixel input limit; the original JPEG/EXIF remains intact. Header identity and answers share the verified homography. `OmrNative` calls `roshd_jni`; recognition uses the retained native OMR implementation, templates and licensed dependencies.

Only signed `scan` packets can be constructed, validated, loaded into the controller's outbox, or submitted. Packets preserve their exact signed request bytes across retries. Only validated server receipts mark a packet delivered. Unreadable entries remain visible as storage errors. Scan-only queue policy rejects other packet kinds.

`ScanQueueSender` streams the eligible outbox in creation order, buffering at most 50 packets and 4 MiB of serialized request data. Each batch belongs to one school. `batchScan` enables `/scanner/scans/batch`; single-only servers retain the full-queue single-request path. Item index, scan ID, outcome, HTTP status and the full receipt are checked independently before committing delivery. Missing or inconsistent receipts stay retryable. Account/transport failures stop later batches. `sendAllScans` runs that stage and then the resumable original-image stage under one controller operation, without nesting asynchronous `run` calls. UI completion requires both the answer receipt and verified image evidence.

Continuous capture uses a separate serial ingestion queue and a durable `camera_work` journal (SQLite schema v2). CameraX may capture the next original while the stage queue admits at most two persisted photos to independent single-page native calls. Immutable recognition requests run on two workers, while grading and persistence return to the serial stage queue. Every completion publishes a scoped immutable `LiveScanFeedback` event before history refresh; it never waits for another page. Account, academic-year/edition and captured round remain bound to each job; metadata-version refreshes do not change that identity. Recovery restores interrupted processing and validates complete reserved JPEGs. JPEG/PNG go directly to the EXIF-aware native reader; other supported formats retain Android conversion. A cached roster index preserves duplicate/expiry/frozen-source checks without repeated full-roster traversal. `WeakHostRegistry` restores the prior native activity when the camera closes. The supported physical families are T1 (100) and T3 (40); the retired family has no template, class or answer worker. Two fresh preview QR reads, focus in the answer area, four stable frames and a 320 ms hold permit guided automatic capture. Native header and signed roster still authorize identity and family. Page content/QR locks prevent duplicate capture. Manual capture remains available. OpenCV distributes available processors across the two original-photo workers without the previous four-thread ceiling. The live path copies luminance only and reuses the QR input buffer, leaving image processing resources for recognition and grading. This is in-process background work with restart recovery, not an Android foreground service.

Roshd network schemas and signature transcripts follow the supplied API contract. Local wrapping-key AAD, private key aliases and native archive magic retain their existing values so stored keys and evidence remain readable. Opaque historical QR bindings come only from the verified current-round roster, and the native header router rejects ambiguous or unknown bindings.

Colored sheets use the same decrypted offline grading calculation to derive per-observation verdicts; no accepted answer sets leave that calculation. `GradedSheet` binds those verdicts to the canonical saved answers and validates native measured bubble geometry. The native renderer writes a unique derived JPEG under the account's private media directory. Its metadata binds the answers and original evidence hash, and a separate archive row references that file. Editing/rereading removes stale color metadata and archive references. Missing geometry on older scans is recovered from verified original evidence, with QR and family rechecked. Regenerating a sealed sheet changes only local annotation metadata; signed requests and original image uploads are preserved. Camera grades are durably saved and published before rendering. A separate background-priority color worker persists annotationPending recovery state and merges only matching source, identity, answers and score snapshots on the stage queue. Rendering failures preserve the score and evidence and display a retryable warning.

Recognition retains local per-question `confidence` and `needsReview` alongside the single highest-fill candidate. Stable local paper permits faint graphite without an absolute gray ceiling; steep/noisy illumination retains stronger contrast requirements. Partial same-hue handwriting requires annulus support and common-print baseline correction. `ScanReview` counts pending questions from the answers themselves, confirms one choice/blank at a time, and gates signing before queue creation. Review metadata is excluded from signed wire answers and offline grading input; uncertain candidates stay neutral in derived color marks. Manual confirmation resolves answer-only engine warnings, while photo/geometry warnings persist. See `MARK_ACCURACY_1.1.30.md`.
